# 파이프라인 설계·실측 노트

RapidOCR + 자체 라벨링 YOLO11n 기반 파이프라인의 구조와 실측 근거를 정리한 문서. 현재 main의 `predict.ipynb`/`pipeline.py`와 같은 로직을 따른다.

---

## 1. 어떤 구조인지

```
사진 한 장
  │
  ├─ [0] 사진 회전 바로잡기
  │       세로로 찍었는데 파일에는 가로로 저장된 사진이 8.7%(293장) 있었음.
  │       이걸 안 맞추면 글자가 누운 채로 들어가서 인식률이 반토막 남.
  │
  ├─ [1] YOLO로 날짜가 적힌 영역 찾기
  │
  ├─ [2] 그 영역만 잘라내기 (여유분 45% 붙여서)
  │       원본 해상도에서 자르기 때문에 글자 크기가 그대로 보존됨.
  │
  ├─ [3] 못 읽은 것만 다음 단계로 넘기는 6단 구조
  │       1차  잘라낸 조각 그대로
  │       2차  잘라낸 조각 + 사진 보정            <- 개선폭이 제일 컸던 단계
  │       3차  잘라낸 조각 + 도트프린터 전용 보정(오츠 이진화 후 팽창)
  │       4차  date/due 타이트 크롭을 RapidOCR 자체 탐지 없이 바로 인식
  │       5차  원본 전체 사진
  │       6차  원본 전체 사진 + 사진 보정
  │
  ├─ [4] 읽어낸 글자를 date_parser.py에 넣어 날짜로 바꾸기
  │       실패한 건에만 보강 레이어를 더 태움 (date_parser_plus.py)
  │
  └─ [5] 그래도 안 되면 월-일만이라도 적어내기

결과: image_id, year, month, day, final_date
```

구조의 핵심은 **앞 단계가 실패한 것만 다음 단계로 넘긴다**는 점임. 보정을 전체 사진에 한꺼번에 걸면 원래 잘 읽히던 것까지 망가질 수 있는데, 실패분에만 걸면 그럴 일이 없음.

## 2. 어떤 데이터셋 활용했는지

| 용도 | 무엇을 |
|---|---|
| YOLO 학습 | 팀이 직접 박스를 라벨링한 자체 검출 데이터셋 |
| YOLO 검증 | 같은 셋의 검증 분할 |
| 최종 성능 측정 | 팀 손라벨 904장 |
| 외부 검증 | `custom_data` 97장(팀 자체 촬영, 학습에 전혀 안 씀) |

글자 읽는 모델은 따로 학습하지 않고 공개된 사전학습 모델을 그대로 썼음.

### 박스 라벨링 절차

`yolo_train/build_dataset.py`에 구현됨.

1. 라벨링 툴(브라우저 캔버스)로 박스 좌표를 JSON으로 기록
2. `ImageOps.exif_transpose`로 EXIF 회전을 픽셀에 반영 — 현재 `pipeline.py`의 `load_bgr()`과 동일 규약. 라벨링 툴은 화면(회전 보정된) 기준으로 좌표를 기록하는데, 원본을 그냥 읽으면 좌표계가 어긋나기 때문(실측: 회전 미보정 시 박스가 이미지 범위를 벗어나는 사례 확인)
3. YOLO 포맷으로 변환
4. 이미지 단위 90/10 분할, 특정 클래스 박스가 양쪽에 고르게 들어가도록 층화

### 평가셋 독립성

배치 A~C(449장)는 검출기 박스 라벨링에 쓰인 이미지다. D+E·F(455장)는 검출기 학습에 한 장도 쓰이지 않은 독립 구간이며, `custom_data` 97장은 검출기·파서 어느 쪽 학습에도 쓰이지 않은 완전한 외부 검증셋이다.

## 3. 모델에 대한 설명

### 영역 찾는 쪽 (YOLO11n)

- 입력 크기 960. 640으로 줄여봤더니 "소비기한" 같은 글자 영역이 세로 14픽셀까지 작아져서 잘 못 찾음. 그래서 960으로 올림.
- 찾는 대상은 네 종류임.

| 이름 | 무엇 |
|---|---|
| `date` | 날짜 숫자 자체 |
| `due` | "소비기한", "유통기한" 같은 안내 문구 |
| `code` | 품목보고번호, 전화번호처럼 날짜로 헷갈리기 쉬운 숫자 |
| `full` | 표시사항이 적힌 라벨 덩어리 전체 |

`code`를 일부러 하나의 종류로 따로 배우게 한 게 포인트임. 안 그러면 품목보고번호를 날짜로 착각하는 일이 생김. 찾아낸 다음에 버리려고 일부러 가르치는 것임.

### 글자 읽는 쪽 (RapidOCR)

- `onnxruntime`만으로 돌아감. torch가 아예 필요 없음.
- YOLO도 onnxruntime으로 직접 추론해 엔진을 하나로 통일함 — torch 의존성 자체가 사라짐.

### 날짜 해석하는 쪽

`date_parser.py`(정규식 규칙 파서)를 기반으로 `date_parser_plus.py`가 실패건에만 보강 레이어를 얹는다. 원래 맞던 건은 안 건드림.

1. 사용기한, 품질유지기한처럼 다르게 적힌 말을 소비기한으로 통일
2. OCR이 헷갈린 글자를 고쳐서 다시 시도 (O와 0, I와 1 같은 것)
3. 구분자 없이 붙여 쓴 표기 (30APR21)
4. 구분자 없는 전숫자 표기 (20260516, 261030)
5. 일자가 아예 안 적힌 포장은 연-월만이라도

## 4. 객관적인 성능은 어떤지

손라벨 904장 기준(A~C 449 + D+E 303 + F 152), 주 지표는 항목별 부분점수.

| 집합 | n | 부분점수 | 완전일치 | 응답률 |
|---|---|---|---|---|
| 전체 | 904 | 85.07% | 80.53% | 91.8% |
| A~C (검출기 학습 + 개발 노출) | 449 | 89.09% | 84.41% | 95.8% |
| D+E | 303 | 79.43% | 74.26% | 87.5% |
| F (봉인, 1회 개봉) | 152 | 84.43% | 81.58% | 88.8% |

속도는 장당 0.56–0.63초. 500장으로 환산하면 280~315초라, 제한 시간 2400초의 12~13%.

### 어디에 시간이 쓰이는지

| 구간 | 걸린 시간 | 비중 |
|---|---|---|
| 사진 불러오기 | 22.6ms | 7.7% |
| YOLO로 영역 찾기 | 39.9ms | 13.5% |
| 글자 읽기 | 232.3ms | 78.7% |
| 사진 보정 | 0.3ms | 0.1% |

1차 경로(가장 흔한 경로) 기준 측정치. 시간을 잡아먹는 건 영역 찾기가 아니라 글자 읽기임. 속도가 문제가 되면 모델을 줄일 게 아니라 글자 읽기를 몇 번 부르는지를 줄여야 함.

### 영역 찾는 모델 자체의 성능

자체 검증 분할 기준, 네 종류를 평균한 mAP50이 0.916임.

| 종류 | mAP50 | 놓치지 않고 찾아낸 비율 |
|---|---|---|
| `date` | 0.984 | 0.964 |
| `full` | 0.952 | 0.906 |
| `due` | 0.894 | 0.818 |
| `code` | 0.833 | 0.763 |

### 449장 시절 단계별 기여도 (참고용, 위 904장 표와 직접 비교 금지)

평가셋이 449장이던 시점의 측정치. 이후 평가셋이 904장으로 늘고 파서·전처리도 여러 차례 바뀌어서, 위 §4 현재 수치와 같은 자로 잰 값이 아님. 단계 도입 순서와 각 단계가 얼마나 기여했는지 감을 잡는 용도로만 남겨둠.

| 구성 | 부분점수 | 완전일치 | 답을 낸 비율 |
|---|---|---|---|
| 글자 인식만 | 72.98% | 68.15% | 77.1% |
| + 월일만이라도 적어내기 | 73.35% | 68.37% | 81.1% |
| + 사진 보정 2단 구조 | 77.21% | 71.71% | 86.0% |
| + YOLO로 잘라내기 | 79.21% | 73.72% | 89.8% |
| + 파서 반영(당시 최신본) | 81.89% | 75.72% | 91.5% |

### 해봤는데 소용없었던 것

학습을 30번에서 150번으로 다섯 배 늘려봤음. 영역 찾는 모델 자체의 점수는 조금 올랐는데, 최종 점수는 아예 안 움직였음(당시 449장 기준, 422장이 완전히 같은 답, 나머지도 개선 10 / 악화 17이라 우연과 구분되지 않는 수준).

## 5. 간단한 브리핑

먼저 **점수를 가른 건 영역 찾는 모델이 아니라 글자 읽는 엔진이었음**(당시 449장 기준). EasyOCR만 썼을 때가 완전일치 39.6%, RapidOCR만 썼을 때가 68.15%였음. YOLO를 붙여서 올라간 폭은 4~5%포인트 수준으로 비교적 작았음. 엔진 선택이 검출기 튜닝보다 레버가 훨씬 컸다는 뜻임.

다음으로 남은 실패는 대부분 사진 자체가 흐린 경우임. 해상도를 올려도 소폭, 파서를 고쳐도 소폭이었던 반면 대비를 높이고 끊긴 점을 이어붙이는 보정은 뚜렷하게 올렸음. 잉크젯으로 점을 찍어 인쇄한 날짜가 특히 안 읽히는데, 라벨링할 때 사람이 "판독불가"로 표시한 것들과 많이 겹침. 사람도 어려운 영역이라는 뜻임.

## 실행 방법

```bash
export ITDA_INPUT_DIR=./val_images
export ITDA_OUTPUT_PATH=./submission.csv

jupyter nbconvert --to notebook --execute predict.ipynb \
    --ExecutePreprocessor.timeout=2400 \
    --output /tmp/executed.ipynb
```

가중치는 `weights/`에 이미 커밋해둠. 받아올 게 없으니 인터넷 없이도 그냥 돌아감.

성능을 직접 재보려면 이렇게 하면 됨.

```bash
python evaluate.py <예측결과.csv> <정답라벨.csv>
```

## 파일 설명

| 파일 | 하는 일 |
|---|---|
| `predict.ipynb` | 채점용 노트북. 이것만 실행하면 됨 |
| `pipeline.py` | 검출-크롭-인식-파싱 전체를 묶은 본체 |
| `date_parser.py` | 정규식 기반 날짜 파서 |
| `date_parser_plus.py` | 파서를 가져다 쓰고 실패분에 보강을 더하는 층 |
| `gap_fill.py` | 파서가 못 잡는 표기 보강 |
| `ocr_normalize.py` | OCR이 헷갈린 글자 고치기 |
| `partial_rescue.py` | 완전 실패했을 때 월-일만이라도 건지기 |
| `preprocess.py` | 대비 높이고 끊긴 글자 이어붙이기 |
| `evaluate.py` | 예측과 정답을 맞춰보고 점수 내기 |
| `config_ko.yaml` | RapidOCR 설정 |
| `weights/` | 영역 찾는 모델과 글자 읽는 모델 |
