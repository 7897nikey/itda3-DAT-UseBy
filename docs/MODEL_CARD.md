# 소비기한 추출 모델 — 구조 · 파라미터 · 성능

한국외대 DAT · UseBy팀 | ITDA 3rd 학술제 본선 | 최종 갱신 2026-09-26

편의점 상품 사진에서 소비기한(연·월·일)을 뽑아내는 파이프라인이다.
채점은 항목별 부분점수이고, 500장을 2,500초 안에 처리해야 한다.
채점 환경은 **Ubuntu 22.04 x86_64 / Python 3.10 / 4코어 / RAM 8GB / 인터넷 차단**이다.

## 1. 구조

```
사진
 └ EXIF 회전 보정                     전체의 8.7%가 세로촬영인데 가로로 저장돼 있음
 └ YOLO11n 영역 검출 @960             4클래스 date / due / code / full
 └ full 우선 크롭 (여유 45%)          full이 없으면 date∪due 합집합
 └ RapidOCR 읽기                      PP-OCRv6_rec_medium
 └ 규칙 파서                          date_parser.py + date_parser_plus.py
 └ 실패분만 다음 단계로 (6단 폴백)
```

**엔진은 onnxruntime 하나로 통일했다.** 검출기도 `.onnx`로 직접 돌려서
torch / ultralytics 의존성이 없다. 실측으로 torch 경로 대비 파이프라인 전체 1.6배,
검출만 놓고 보면 7.1배 빠르다(큰 사진 한 장 6.16초 → 0.41초).

### 6단 폴백

| 단계 | 경로 | D+E 303장에서 최종 답을 낸 수 |
|---|---|---|
| 1 | 크롭 → OCR | **239** |
| 2 | 크롭 + CLAHE 보정 | 19 |
| 3 | 크롭 + 도트프린터 보정 | 6 |
| 4 | 타이트 크롭 직접 인식 (Det 우회) | **23** |
| 5 | 전체 이미지 | 0 |
| 6 | 전체 + 보정 | 3 |
| — | 무응답 | 13 |

연·월·일을 **다 채운 답이 나오면 끊고**, 아니면 끝까지 돌면서 가장 많이 채운 답을
남긴다. 부분 답에서 멈추면 뒤 단계가 찾았을 완전한 날짜를 놓친다(실측 회귀 있었음).

**1단계와 4단계가 OCR을 다르게 쓴다.** 1단계는 RapidOCR의 텍스트 검출을 거쳐
크롭 안에서 글자줄을 찾고, 4단계는 검출을 건너뛰고 크롭 전체를 한 줄로 읽는다
(`use_det=False`). 이 차이가 아래 파라미터 감도를 갈라놓는다.

그래도 실패하면 **월-일만이라도 제출한다.** NONE은 확정 0점이기 때문이다.

## 2. 파라미터

전부 실측으로 정했다. `검증` 열은 전수 탐색 여부다.

| 값 | 현행 | 근거 | 검증 |
|---|---|---|---|
| `imgsz` | 960 | 640에서는 due 박스가 세로 14px까지 작아져 못 찾음 | 2값 |
| `conf_thresh` | 0.25 | **0.15~0.35가 전부 같은 출력.** 무감 구간 한가운데 | **7값 전수** |
| `pad` (메인 크롭) | 0.45 | 무릎점. 아래는 손해, 위는 평지인데 속도만 +39% | **9값 전수** |
| `upscale` | 100 | **지금 발동해도 답을 안 바꿈.** 비용 0인 보험으로 유지 | **7값 전수** |
| `tightpad` (4단계) | 0.10 | 위쪽이 절벽. 0.60에서 개선 0 / 퇴행 13 | **7값 전수** |
| `unclip_ratio` | 2.2 | 1.6 대비 +2.75%p. 1.9~3.2 전수 탐색의 꼭대기 | 전수 |
| `clipLimit` (CLAHE) | 3.0 | 2.0 대비 +1.68%p | 2값 |
| `limit_side_len` | 736 | 960·1280은 각각 -3.9%p, -6.6%p로 유의하게 악화 | 3값 |
| 인식 모델 | `PP-OCRv6_rec_medium` | 이전 모델 대비 F 기준 +4.82%p (p=0.019) | 2값 |

### 크롭 파라미터의 감도가 서로 반대인 이유

메인 `pad`는 0.45 위가 **평지**인데 `tightpad`는 0.10 위가 **절벽**이다.
같은 "크롭 여유율"인데 방향이 반대다.

메인 크롭은 뒤에 **텍스트 검출기가 돌기 때문에** 여백이 넓어도 검출기가 글자줄을
알아서 찾아낸다. 타이트 크롭은 **검출을 건너뛰고 전체를 한 줄로 읽으므로**
여백이 곧 오염이다 — 옆 인쇄물이 같은 줄에 섞여 들어간다.

> **최적 여유율은 "뒤에 텍스트 검출기가 도는가"에 달려 있다.**

### conf_thresh가 넓은 무감 구간을 갖는 이유

`full` 박스가 **302/303장에서 잡히고 그중 300개가 신뢰도 0.50 이상**이다.
크롭은 `full`을 신뢰도순으로 정렬해 **상위 2개만** 쓰므로, 문턱을 0.15~0.35로
움직여 들어오고 나가는 낮은 신뢰도 박스들이 선택에 영향을 주지 못한다.
`code` 클래스는 파이프라인이 아예 쓰지 않는다.

**취약점이 아니라 안전 마진이다.** 문턱을 두 배 이상 움직여도 결과가 같다는 것은
평가셋 분포가 달라도 이 파라미터가 흔들리지 않는다는 뜻이다.

## 3. 성능

### 주 지표 — 홀드아웃 294장

판단에 한 번도 쓰지 않은 데이터다. **보고 시 이 수치를 쓴다.**

| | 예선 제출본 | **현재** |
|---|---|---|
| 부분점수 | 81.23% | **92.61%** |
| 완전일치 | 75.43% | **88.05%** |
| 응답률 | 88.7% | **97.6%** |

개선폭 **+11.38%p**, 95% CI `[+7.62, +15.24]`, 개선 56 / 퇴행 10,
부호검정 p < 0.0000001. **부호검정과 부트스트랩이 둘 다 통과한다.**

2026-09-25~26에 라벨을 인쇄와 대조해 교정한 뒤 `predict.ipynb`를 다시 실행해 잰 값이다(모델 무변경).
예선 제출본도 같은 라벨로 다시 채점했다. 교정 전 값은 92.49% / 87.71%, 개선폭 +11.49%p였다.

교정은 모델 예측을 보지 않고 인쇄만 기준으로 했다. 그래서 점수가 양쪽으로 움직였다 — 9/25 교정
후 92.83%까지 올랐다가, 9/26 전수 감사 후 92.61%로 내려왔다. 홀드아웃에서 새로 고친 3건 중 2건
(터키 제품)은 **모델도 라벨러와 똑같이 잘못 읽고 있었기** 때문이다. 라벨이 정확해질수록 모델의
진짜 약점이 드러난다(5절 ⑤).

> 평가셋 904장 기준으로는 93.18%지만 배치 A~C가 개발에 노출돼 부풀려져 있다.
> 공식 수치로 쓰지 않는다.

### 개선 단계별 기여

| 단계 | 904장 | 근거 |
|---|---|---|
| 예선 제출본 | 84.66% | |
| + 인식 모델 `PP-OCRv6_rec_medium` | 90.01% | F 기준 +4.82%p (p=0.019) |

이 표는 단계별 이력이다. 2026-09-26 기준 현행 모델과 현행 라벨로 904장을 다시 재면 **93.18%**다

## 4. 검증 규율

이 프로젝트가 지키는 규칙이다. 수치를 읽을 때 같이 봐야 한다.

1. **판단은 D+E 303장에서만.** A~C는 개발에 노출됐고 F는 소진됐다.
2. **홀드아웃 294장은 최종 확인 1회용.**
3. **개선폭은 튜닝 집합이 약 2배로 부풀린다.** 실측: 인식기 교체가
   D+E에서 +9.24%p인데 F에서는 +4.82%p였다. **F 쪽 숫자를 보고한다.**
4. **부호검정과 부트스트랩을 같이 본다.** 부호검정은 차이의 크기를 버려서
   너무 보수적이다.
5. **퇴행 건수를 반드시 센다.** 평균이 올라도 퇴행이 많으면 위험하다.
6. **속도는 반복 측정한다.** 출력이 완전히 같은 두 실행이 장당 0.917초와
   1.471초로 찍힌 적이 있다.

## 5. 알려진 한계

**① 홀드아웃이 검출 단계에서는 독립이 아니다.** 294장 전부가 YOLO 학습에 들어 있다.
원본 3,352장 중 2,892장이 학습에 쓰여서 검출까지 독립인 홀드아웃은 만들 수 없었다
(남는 게 2장). 검출기가 안 본 808장에서 mAP50 0.917이라 추가 이득은 작다고 본다.

**② 연도 사전은 데이터 의존 가정이다.** 2자리 연도 자리 판정이 쓰는 연도 분포는
741장에서 뽑았다. 평가셋 분포가 다르면 역효과일 수 있다. 2030·2018은 사전에 없다.

**③ 읽기순서 정렬은 지금 효과가 0이다.** 이식 당시 근거(+1.9%p)는 이전 인식 모델
기준이었다. 재측정하니 개선 1 / 퇴행 1로 +0.00%p다. **점수에 기여한다고 말하지 않는다.**

**④ 라벨 신뢰도는 교차검증과 전수 감사로 확인했다.** 30장을 세 명이 기존 라벨을 보지
않고 다시 달았다. 두 명은 기존 정답과 30/30 일치했고, 나머지 한 명의 불일치 4건은 인쇄를
열어보니 모두 기존 정답이 맞았다. 월·일이 모두 12 이하인 모호 라벨 **431건을 인쇄와 전수
대조**해 3건을 교정했고, 교정은 한 라벨러의 라벨에만 몰려 있었다(나머지 294건은 0건).
그 라벨러의 라벨 397건은 **전부** 인쇄와 대조해 10건을 더 교정했다(9/26). 교정 후 904장에서
현행 모델의 라벨러별 실패율은 8.64 / 10.63 / 9.93%로 차이가 없다(Fisher p=0.48).
예전에 보고했던 라벨러 간 점수 편차 8.15%p는 지금 모델·라벨로는 나타나지 않는다.
전수 감사는 한 라벨러에게만 했으므로 나머지 라벨에 남은 오류는 이 수치에 반영되지 않았다.

**⑤ 외국 제품의 2자리 연도 표기를 한국식으로 읽는다.** 터키 제품의 `26.02.21`을
`YY.MM.DD`(2026-02-21)로 읽는다. 실제로는 일.월.년(2021-02-26)이다. 2자리 연도 판정이
원산지·언어를 보지 않고 연도 사전만 보기 때문이다. 외국어 표지(`TETT`, `BEST BEFORE` 등)로
일/월/년을 택하는 규칙을 넣을 수 있지만, **이 약점은 홀드아웃에서 찾아서 고치지 않았다.**
판단 집합(D+E)에는 같은 사례가 없어 검증할 수 없고, 같은 홀드아웃으로 재면 부풀려진다.

**⑥ "제조일로부터 N개월"이 날짜와 떨어져 인쇄되면 못 읽는다.** 생수병처럼 날짜 옆에는
제조일만 있고 기한 문구는 라벨 뒷면에 있는 경우, 크롭 안에 문구가 없어 제조일을 답으로 낸다.

## 6. 남은 실패의 구조

D+E 303장에서 32장이 틀린다(잃은 항목 73/909, 8.0%).
**32장 중 16장이 인식이 아니라 파서·폴백 문제다.**

| 원인 | 건수 |
|---|---|
| 제조일을 소비기한으로 오선택 | 6 |
| 폴백 조기종료로 정답 버림 | 4 |
| 공백 구분 날짜 (`19 102022`) | 4 |
| 월-연 표기인데 일을 만들어냄 | 2 |
| 자리 판정 (연↔일) | 3 |
| 진짜 인식 실패 | 7 |
| 기타 (숫자열 파묻힘, 라벨 의문) | 6 |

9/23에 "인식 실패"로 분류했던 002833과 "한 자리 오독"으로 본 001478은 9/26 라벨 감사에서
**라벨 오류로 밝혀졌다.** 모델이 맞게 읽고 있었다. 실패 분석도 라벨이 틀리면 틀린다.

**검출이 못 찾은 건 0건이다.** 가장 큰 덩어리인 "제조일 오선택 6건" 중 3건은
`EXP` / `Best before` 키워드가 정답 쪽에 붙어 있는데도 제조일을 골랐다.

> 이 항목들은 **찾았지만 적용하지 않았다.** 고칠 수는 있으나 퇴행을 잡아낼 깨끗한
> 검증 집합이 남아 있지 않다. 고치면 "고쳤는데 좋아졌는지 모르는" 상태가 된다.
