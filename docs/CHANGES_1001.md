# 10/1 최종 개선 요약 (팀 공유용)

**한 줄 요약.** 모델·가중치는 그대로 두고 날짜 파서와 폴백 순서만 고쳤습니다.
새로 라벨링한 홀드아웃 K(297장)에서 **88.55% → 90.35% (+1.80%p), 개선 9 / 퇴행 0**이고,
부호검정과 부트스트랩이 모두 통과했습니다. 속도는 그대로입니다.

---

## 1. 무엇을 고쳤나

9/23 실패 분석에서 "인식이 아니라 파서·폴백이 못 받는다"고 찾아 놓고, 검증할 깨끗한
데이터가 없어 미뤄 두었던 항목들입니다. 이번에 홀드아웃 K를 새로 만들어 적용했습니다.

| # | 문제 | 실제 사례 (OCR 원문) | 고친 것 | 파일 |
|---|---|---|---|---|
| 1 | 제조일을 소비기한으로 고름 | `Prod date: 13/03/2020 Best before: 06/11/2020` | 키워드 판정에서 대소문자를 무시하고, 제조일 키워드에 `PRO:` `MFD`를 추가 | `date_parser.py` |
| 2 | 뒤 날짜의 EXP 라벨을 앞 날짜가 가로챔 | `1AN:14/09/2020 EXP:14/09/2021` | 키워드가 날짜 **앞**에 붙은 후보를 우선 | `date_parser.py` |
| 3 | 월-연을 일로 쪼갬 | `BEST BEFORE END: Nov 2021` → 2021-11-**20** | 4자리 연도를 일+연으로 쪼개지 않음 → 2021-11-NONE | `date_parser.py` |
| 4 | 영문 월의 연도 자리 오판 | `BEST BEFORE 17 JUL 21` → **2017**-07-21 | 영문 표기는 일-월-연을 기본으로 함(연도 사전이 강하게 반대할 때만 예외) | `date_parser.py` |
| 5 | 영문 표기 순서 안내 무시 | `Best Before 07 09 21 (DD/MM/YY)` | `DD/MM/YY` `YY/MM/DD` 안내를 읽음 | `date_parser.py` |
| 6 | 공백으로 끊긴 2자리 연도 날짜 | `30 12 23`, `19 102022` | 크롭 텍스트에서만, 세 자리 모두 2자리일 때 인식 | `gap_fill.py` |
| 7 | 기한 표지 바로 뒤 월-연을 놓침 | `LOT 502337-04 EXP 02/2023`, `EXP:01.2022` | 표지와 날짜 사이에 다른 숫자가 없으면 월-연으로 받음 | `gap_fill.py` |
| 8 | `OCT.2021` 형식 월-연 | `avant fin: OCT.2021` | 영문 월과 연도 사이 점·슬래시 허용 | `gap_fill.py` |
| 9 | **숫자를 흘린 답에서 멈춤** | 1단계 `2026.1 .05`, 4단계 `2020.12`(→2020-01-02) | 월·일 자릿수가 모자란 "약한 완성답"이면 멈추지 않고 다음 단계를 더 봄. 뒤에서 온전한 답이 나오면 그걸 쓰고, 없으면 원래 답 유지 | `predict.ipynb`, `pipeline.py` |

**측정했지만 넣지 않은 것.** "모든 완성답에서 다음 단계까지 더 보기"는 개선 4건(p=0.125)에 비해
크롭 OCR 호출이 4배 이상 늘어 기각했습니다. 9번은 약한 답에서만 더 돌기 때문에 단계 실행이
약 11% 느는 데 그칩니다.

## 2. 점수

모든 수치는 `predict.ipynb`를 실제로 실행해 잰 값입니다. 채점은 팀 규칙대로 `status=완료`만 셉니다.
"9/26 확정본"은 이번 변경 직전의 제출본(`0b0fe82`)입니다.

### ① 새 홀드아웃 K — 주 근거

이번에 새로 뽑아 라벨링한 300장 중 판독 가능한 297장입니다. 어떤 결정에도 쓰지 않았고,
**모델을 확정한 뒤 딱 한 번 열었습니다.**

| | 9/26 확정본 | **10/1 최종본** |
|---|---|---|
| 부분점수 | 88.55% | **90.35%** |
| 완전일치 | 83.16% | **86.20%** |
| 응답률 | 94.9% | 95.6% |
| 연 / 월 / 일 | 89.2 / 90.9 / 85.5% | **90.2 / 92.6 / 88.2%** |

**+1.80%p, 95% CI [+0.67, +3.14], 개선 9 / 퇴행 0, 부호검정 p=0.0039.**

### ② 평가셋 904장 — 참고 (A~C는 개발에 노출돼 부풀려져 있음)

| 집합 | n | 9/26 확정본 | **10/1 최종본** | 개선 / 퇴행 |
|---|---|---|---|---|
| 전체 | 904 | 93.18% | **95.50%** | 34 / 0 |
| A–C | 449 | 94.80% | 96.36% | 13 / 0 |
| D+E | 303 | 91.97% | 95.38% | 14 / 0 |
| F | 152 | 90.79% | 93.20% | 7 / 0 |

완전일치 90.27% → 93.92%. 전체 +2.32%p, 95% CI [+1.51, +3.17].

### ③ 기존 점수와의 관계

| 지표 | 이전 보고치 | 지금 |
|---|---|---|
| 홀드아웃 294장 (9/17 개봉) | 92.61% | 95.90% — **이제 주 근거로 쓰지 않음** |
| 평가셋 904장 | 93.18% | 95.50% |
| **새 홀드아웃 K 297장** | — | **90.35%** |
| 팀 자체 촬영 custom_data 97장 | 80.41% | 82.47% (개선 4 / 퇴행 0) |

**왜 294장 대신 K를 주 근거로 바꾸나.** 이번 규칙 중 7·9번은 294장의 실패 원문을 보고
설계했습니다. 294장은 이제 개발용 데이터라서, 거기서 나온 95.90%는 낙관치입니다.

**왜 K 점수가 294장보다 낮나.** K가 더 어려운 표본입니다. 같은 9/26 확정본으로 재도
294장 92.61%, K 88.55%입니다. 모델이 나빠진 게 아니라 자가 바뀐 것이고, 비교는 반드시
같은 집합 안에서 짝지어 합니다.

### ④ 튜닝 집합 부풀림이 또 확인됨

개발용 596장(D+E + 294장)에서는 +3.36%p였는데 새 홀드아웃에서는 +1.80%p였습니다.
**약 1.9배**로, 인식기 교체 때 실측한 약 2배(D+E +9.24%p 대 F +4.82%p)와 같습니다.

### ⑤ 속도

맥(arm64) 같은 이미지 597장 기준 장당 1.014초 → 1.011초로 차이가 없습니다. 단계 실행 횟수로 계산한
상한은 약 +11%입니다. x86 실측은 이번 push로 도는 `verify-x86` CI에서 확인합니다.

## 3. 검증 방법과 한계

- **홀드아웃 K 선정.** `splits/holdout_G/candidates_safe.csv`에서 이미 쓴 300장을 빼고, 기존 라벨본과
  지각 해시 거리 20 이하(연사본)를 뺀 뒤 고정 시드 `20261001`로 300장을 뽑았습니다. `splits/holdout_K/`
- **라벨 감사.** 김건우 단독 라벨입니다. **모델 예측을 보기 전에** 월·일이 둘 다 12 이하인 89건과
  연도 이상치를 인쇄와 대조해 12건을 고쳤습니다. 연도가 맨 뒤인 날짜를 월/일로 읽는 습관이
  7건 다시 나왔습니다(9/25 감사와 같은 방향). 기록은 `splits/holdout_K/AUDIT_1001.md`,
  원본은 `labels_K_raw.csv`에 있습니다.
  - 002705/002706은 미국 제품이라 실제로는 월/일일 수 있습니다. 대회 규칙("연도가 맨 뒤면 일/월/년")에
    맞췄습니다. 감사 전 원본 라벨로 채점해도 개선 9 / 퇴행 0, +1.57%p로 결론은 같습니다.
- **K도 검출기 학습 이미지에서 뽑았습니다.** 기존 홀드아웃과 같은 한계입니다. 짝지은 비교는
  양쪽이 같은 검출기를 쓰므로 변화량에는 영향이 거의 없습니다.
- **K는 이제 열렸습니다.** 이 결과를 보고 다시 고치면 K도 개발용이 됩니다.

예측 원본 CSV는 `docs/results_1001/`에 있습니다.
