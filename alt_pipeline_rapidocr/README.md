# RapidOCR 기반 파이프라인 (KGW)

main 브랜치의 `date_parser.py` 그대로 가져다 썼음. 엔진은 RapidOCR로 바꿨고 자잘한 거 보강했음.

main 브랜치 파일은 한 개도 안 건드렸고 이 폴더만 새로 추가함.

---

## 1. 어떤 구조인지

```
사진 한 장
  │
  ├─ [0] 사진 회전 바로잡기
  │       세로로 찍었는데 파일에는 가로로 저장된 사진이 8.7%(293장) 있었음.
  │       이걸 안 맞추면 글자가 누운 채로 들어가서 인식률이 반토막 남.
  │
  ├─ [1] YOLO로 날짜가 적힌 영역 찾기
  │
  ├─ [2] 그 영역만 잘라내기 (여유분 30% 붙여서)
  │       원본 해상도에서 자르기 때문에 글자 크기가 그대로 보존됨.
  │
  ├─ [3] 잘라낸 조각만 RapidOCR로 읽기
  │
  ├─ [4] 못 읽은 것만 다음 단계로 넘기는 4단 구조
  │       1차  잘라낸 조각 그대로
  │       2차  잘라낸 조각 + 사진 보정            <- 개선폭이 제일 컸던 단계
  │       3차  원본 전체 사진
  │       4차  원본 전체 사진 + 사진 보정
  │
  ├─ [5] 읽어낸 글자를 main의 date_parser.py에 넣어 날짜로 바꾸기
  │       실패한 건에만 보강 네 겹을 더 태움 (date_parser_plus.py)
  │
  └─ [6] 그래도 안 되면 월-일만이라도 적어내기
          채점이 항목별 부분점수라 NONE은 무조건 0점임. 틀려도 0점이니
          찍는 쪽이 손해볼 게 없음.

결과: image_id, year, month, day, final_date
```

구조의 핵심은 앞 단계가 실패한 것만 다음 단계로 넘긴다는 점임. 보정을 전체 사진에 한꺼번에 걸면 원래 잘 읽히던 것까지 망가질 수 있는데, 실패분에만 걸면 그럴 일이 없음. 449장으로 확인했을 때 이 방식에서 새로 틀린 건 0건이었음.

## 2. 어떤 데이터셋 활용했는지

| 용도 | 무엇을 | 몇 장 |
|---|---|---|
| YOLO 학습 | 운영진이 준 archive.zip 라벨 | 2,892장 |
| YOLO 검증 | archive.zip 검증분 | 808장 |
| 최종 성능 측정 | 팀에서 손으로 라벨링한 것 | 449장 |

손라벨 450장은 학습에 한 장도 안 씀. 원래 archive.zip 학습분 3,343장 안에 이 450장이 섞여 있어서, 그걸 빼고 연속 촬영으로 거의 같은 사진인 5장까지 추가로 뺀 게 2,892장임.

이걸 왜 굳이 했냐면, 학습에 쓴 사진으로 성능을 재면 점수가 실제보다 높게 나오기 때문임. 처음에는 배치 A와 C 300장만 뺀 상태로 돌렸는데, 나중에 배치 B를 합쳐서 확인해보니 B의 148장이 학습셋에 그대로 들어가 있었음. 학습 초반에 발견해서 데이터를 다시 만들고 처음부터 다시 돌렸음.

글자 읽는 모델은 따로 학습하지 않고 공개된 사전학습 모델을 그대로 썼음.

## 3. 모델에 대한 설명

### 영역 찾는 쪽 (YOLO11n)

- 입력 크기 960. 640으로 줄여봤더니 "소비기한" 같은 글자 영역이 세로 14픽셀까지 작아져서 잘 못 찾음. 그래서 960으로 올림.
- 찾는 대상은 네 종류임.

| 이름 | 무엇 |
|---|---|
| `date` | 날짜 숫자 자체 |
| `due` | "소비기한", "유통기한" 같은 안내 문구 |
| `code` | 품목보고번호, 전화번호처럼 날짜로 헷갈리기 쉬운 숫자 |
| `full` | 표시사항이 적힌 라벨 덩어리 전체 |

`code`를 일부러 하나의 종류로 따로 배우게 한 게 포인트임. 안 그러면 품목보고번호를 날짜로 착각하는 일이 생김. 찾아낸 다음에 버리려고 일부러 가르치는 것임.

### 글자 읽는 쪽 (RapidOCR)

- `onnxruntime`만으로 돌아감. torch가 아예 필요 없음.
- main 쪽 파이프라인이 EasyOCR용 torch 버전과 ultralytics가 요구하는 torch 버전 사이에서 충돌이 났었는데, 이쪽은 torch를 안 쓰니까 그 문제 자체가 없어짐. 팀원이 YOLO를 ONNX로 내보내서 푼 문제를 다른 방향으로 푼 셈임.

### 날짜 해석하는 쪽

main의 `date_parser.py`를 그대로 씀. 복사해오지 않고 import로 불러오기 때문에, main 파서를 고치면 이쪽도 자동으로 따라감.

그 위에 `date_parser_plus.py`가 네 겹을 더 얹음. main 파서가 실패한 건에만 도는 구조라 원래 맞던 건은 안 건드림.

1. 사용기한, 품질유지기한처럼 다르게 적힌 말을 소비기한으로 통일
2. OCR이 헷갈린 글자를 고쳐서 다시 시도 (O와 0, I와 1 같은 것)
3. 구분자 없이 붙여 쓴 표기 (30APR21)
4. 일자가 아예 안 적힌 포장은 연-월만이라도

## 4. 객관적인 성능은 어떤지

라벨을 904장까지 늘리고 다시 쟀음. 그런데 이 평균을 그대로 쓰면 안 됨.

| 집단 | 장수 | 부분점수 | 완전일치 | 못 읽은 비율 |
|---|---|---|---|---|
| A~C (개발하면서 계속 본 것) | 449 | 84.63% | 78.8% | 7.3% |
| D~F (한 번도 안 본 것) | 455 | 73.04% | 68.1% | 16.3% |
| 전체 | 904 | 78.80% | 73.45% | 11.8% |

**처음 보는 사진에서의 성능은 73% 근처임. 84.63%는 11.6%포인트 부풀려진 값임.**

이 격차가 사진이 어려워서 생긴 게 아님을 확인했음. D~F가 해상도가 조금 낮긴 한데
(긴 변 중앙 1,084 대 1,253) 해상도 구간을 갈라서 비교해도 모든 구간에서 격차가 나고
오히려 고해상도에서 더 큼 (-15.7%포인트). D~F를 A~C의 해상도 분포에 맞춰 보정해도
72.48%로 거의 안 변함.

원인은 개발 과정에 있음. `gap_fill`, `ocr_normalize`, 별칭 정규화를 전부 A~C의 실패를
열어보면서 만들었음. 학습에서 뺐으니 괜찮다고 생각했는데, 실패 사례를 반복해서 보고
규칙을 고치는 것만으로도 같은 일이 벌어짐. 모델 가중치가 아니라 코드로 새어 들어간 것임.

그래서 앞으로 성능 판단은 D~F 455장으로 함. A~C를 섞으면 진짜 개선이 희석되거나
반대로 보임.

여기까지 쌓아 올린 과정은 이랬음 (449장 기준이라 위 표보다 높게 나옴).

| 구성 | 부분점수 | 완전일치 |
|---|---|---|
| 글자 인식만 | 72.98% | 68.15% |
| + 월일만이라도 적어내기 | 73.35% | 68.37% |
| + 사진 보정 2단 구조 | 77.21% | 71.71% |
| + YOLO로 잘라내기 | 79.21% | 73.72% |
| + main 파서 최신본 반영 | 81.89% | 75.72% |
| + 글자 박스 넓히기 | 84.63% | 78.84% |

속도는 장당 0.42초. 500장으로 환산하면 210초라, 제한 시간 2400초의 8.8%임. 여유가 꽤 있음.

### 글자 박스 넓히기 (unclip_ratio 1.6 -> 2.2)

OCR이 글자를 찾을 때 치는 네모를 얼마나 부풀릴지 정하는 값임. 기본값 1.6은 보통 문서 기준이라, 포장지처럼 흐릿하거나 잉크젯으로 점 찍어 인쇄한 글자에는 네모가 좁아서 가장자리가 잘렸음.

| 값 | 부분점수 | 완전일치 | 장당 |
|---|---|---|---|
| 1.6 (기본값) | 81.89% | 75.72% | 0.599초 |
| 1.9 | 83.59% | 77.28% | 0.411초 |
| 2.2 (채택) | 84.63% | 78.84% | 0.393초 |
| 2.5 | 83.82% | 77.51% | 0.396초 |
| 2.8 | 83.00% | 76.61% | 0.426초 |
| 3.2 | 82.11% | 74.39% | 0.435초 |

정확도가 오르면서 속도도 같이 빨라졌음. 한 번에 읽히는 비율이 올라가서 다시 읽는 단계를 덜 타기 때문임.

449장을 무작위로 반반 갈라서 다섯 번 확인했는데 다섯 번 다 양쪽에서 올랐음. 특정 종류에만 몰린 것도 아님 (판독불가 +6.41%포인트, 참조표기 +3.89%포인트, 태그없음 +2.92%포인트). 흐린 사진에서 이득이 제일 큰 게 원리와도 맞음.

다만 2.2와 2.5는 449장으로는 구분이 안 됨. 2.2를 고른 근거는 값 하나하나를 맞대본 결과가 아니라, 올라갔다 내려오는 곡선의 꼭대기라는 모양 자체임.

이 속도는 이미 채점 환경 조건으로 잰 값임. YOLO를 CPU로 돌리고 글자 인식도 4개 코어만 쓰도록 묶어놓고 측정했음. 다만 기계가 맥이라, x86 서버에서 코어 하나당 성능이 얼마나 다른지는 아직 못 재봤음.

### 어디에 시간이 쓰이는지

| 구간 | 걸린 시간 | 비중 |
|---|---|---|
| 사진 불러오기 | 22.6ms | 7.7% |
| YOLO로 영역 찾기 | 39.9ms | 13.5% |
| 글자 읽기 | 232.3ms | 78.7% |
| 사진 보정 | 0.3ms | 0.1% |

시간을 잡아먹는 건 영역 찾기가 아니라 글자 읽기임. 나중에 속도가 문제가 되면 모델을 줄일 게 아니라 글자 읽기를 몇 번 부르는지를 줄여야 함.

### 영역 찾는 모델 자체의 성능

검증용 808장으로 잰 값이고, 네 종류를 평균한 mAP50이 0.916임.

| 종류 | mAP50 | 놓치지 않고 찾아낸 비율 |
|---|---|---|
| `date` | 0.984 | 0.964 |
| `full` | 0.952 | 0.906 |
| `due` | 0.894 | 0.818 |
| `code` | 0.833 | 0.763 |

### 해봤는데 소용없었던 것

학습을 30번에서 150번으로 다섯 배 늘려봤음. 영역 찾는 모델 자체의 점수는 조금 올랐는데, 최종 점수는 아예 안 움직였음. 449장 중 422장이 완전히 같은 답이 나왔고 나머지도 좋아진 게 10장 나빠진 게 17장이라, 우연으로 볼 수 있는 수준이었음.

열 시간을 써서 얻은 건 성능이 아니라 이 방향은 더 팔 게 없다는 확인임. 그래도 다음에 같은 삽질을 안 하게 됐으니 남는 게 없지는 않다고 봄.

## 5. 간단한 브리핑

지금까지 확인한 걸 정리하면 이렇게 됨.

먼저 **점수를 가른 건 영역 찾는 모델이 아니라 글자 읽는 엔진이었음**. EasyOCR만 썼을 때가 완전일치 39.6%, RapidOCR만 썼을 때가 68.15%였음. 여기에 YOLO를 붙여서 올라간 폭은 양쪽 다 4에서 5%포인트 정도로 비슷했고, 영역 찾는 모델 점수도 0.924 대 0.916으로 거의 같음. 학습에 쓴 데이터가 서로 달라서 두 파이프라인의 최종 점수를 직접 비교할 수는 없지만, 적어도 엔진을 바꿨을 때 올라가는 폭이 YOLO를 손볼 때보다 훨씬 크다는 건 분명함. 지금 당장 점수를 올리려면 엔진 쪽이 빠른 길임.

다음으로 남은 실패는 더 이상 못 읽는 게 아니라 엉뚱한 날짜를 고르는 쪽임. 449장 중 못 읽는 건 33장까지 줄었는데 읽고도 틀리는 게 62장임. 처음에는 못 읽는 게 103장 틀리는 게 40장이었으니 완전히 뒤집혔음. 못 읽는 쪽은 해상도를 올려도 1.26%포인트밖에 안 오르고 파서를 고쳐도 0.37%포인트뿐이었음. 반면 대비를 높이고 끊긴 점을 이어붙이는 보정은 3.86%포인트를 올렸음. 잉크젯으로 점을 찍어 인쇄한 날짜가 특히 안 읽히는데, 라벨링할 때 사람이 "판독불가"로 표시한 것들과 많이 겹침. 사람도 어려운 영역이라는 뜻임. 그러니 앞으로는 안 읽히는 사진을 붙잡고 있기보다, 읽어낸 날짜 중에 무엇을 고를지를 손보는 쪽이 남는 장사임. 실제로 틀린 62장 중 40장이 연월일을 통째로 잘못 골랐음. "30/04/21"을 2030년 4월 21일로 읽었는데 실제로는 2021년 4월 30일인 식임.

마지막으로 라벨을 904장까지 늘린 것이 가장 값진 일이었음. 449장일 때는 자잘한 차이를 아예 못 쟀고(unclip 2.2와 2.5를 구분 못 했음), 무엇보다 우리 성능이 11.6%포인트 부풀려져 있다는 걸 몰랐음. 새 라벨 455장이 들어오자마자 바로 드러났음. 앞으로도 라벨을 더 붙이는 게 어떤 파라미터를 만지는 것보다 확실한 투자라고 봄.

덧붙여, 정주희님이 제안한 clipLimit 3.0을 반영했음. D~F 455장에서 +1.68%포인트임(개선 12 / 퇴행 4). 같이 제안된 pad 0.45 + upscale 100은 D~F에서 +1.90%포인트로 더 좋지만, 그 설정에서 세그멘테이션 폴트가 여섯 번 났음. 채점 도중에 한 번 나면 0점이라 원인을 밝히기 전까지는 안 넣는 게 맞다고 봄.

## 실행 방법

```bash
cd alt_pipeline_rapidocr
pip install -r requirements.txt

export ITDA_INPUT_DIR=./val_images
export ITDA_OUTPUT_PATH=./submission.csv

jupyter nbconvert --to notebook --execute predict.ipynb \
    --ExecutePreprocessor.timeout=2400 \
    --output /tmp/executed.ipynb
```

가중치 두 개는 `weights/`에 이미 커밋해둠. 받아올 게 없으니 인터넷 없이도 그냥 돌아감. main의 `download_weights.sh`는 EasyOCR용이라 이 폴더에는 필요 없음.

`region_best.pt`는 우리가 직접 학습한 거라 다시 받을 데가 없고, `korean_PP-OCRv5_rec_mobile.onnx`는 공개 모델이지만 채점 서버가 오프라인이라 어차피 미리 있어야 함. 그래서 팀원이 `yolo_exp_mfg.onnx`를 커밋한 것과 같은 이유로 둘 다 커밋했음. 합쳐서 18MB임.

성능을 직접 재보려면 이렇게 하면 됨.

```bash
python evaluate.py <예측결과.csv> <정답라벨.csv>
```

## 숫자를 비교할 때 주의할 점

main README에 적힌 완전일치 44%와 위의 숫자를 나란히 놓고 보면 안 됨. 쓴 데이터가 서로 다름.

팀원 쪽 YOLO는 팀원이 따로 만든 별개의 데이터셋으로 학습했음. 우리가 날짜를 라벨링한 450장과는 다른 셋임. 이쪽 YOLO는 운영진이 준 archive.zip으로 학습했고, 450장은 학습에서 통째로 빼놓고 성능 재는 용도로만 썼음.

그러니까 두 숫자는 서로 다른 재료로 만들어 서로 다른 자로 잰 값임. 어느 쪽이 낫다는 근거로 쓰기는 어렵고, 각자 자기 구성 안에서 얼마나 올랐는지를 보는 게 맞음. 그렇게 보면 YOLO를 붙여서 올라간 폭은 양쪽 다 4에서 5%포인트 정도로 비슷했음.

팀 차원에서 평가셋과 재는 방법을 하나로 맞춰두면 좋겠음. 그래야 앞으로 누가 뭘 고쳤을 때 그게 진짜 나아진 건지 바로 알 수 있음.

## 파일 설명

| 파일 | 하는 일 |
|---|---|
| `predict.ipynb` | 채점용 노트북. 이것만 실행하면 됨 |
| `pipeline.py` | 검출-크롭-인식-파싱 전체를 묶은 본체 |
| `date_parser_plus.py` | main 파서를 가져다 쓰고 실패분에 보강을 더하는 층 |
| `gap_fill.py` | main 파서가 못 잡는 표기 보강 |
| `ocr_normalize.py` | OCR이 헷갈린 글자 고치기 |
| `partial_rescue.py` | 완전 실패했을 때 월-일만이라도 건지기 |
| `preprocess.py` | 대비 높이고 끊긴 글자 이어붙이기 |
| `evaluate.py` | 예측과 정답을 맞춰보고 점수 내기 |
| `config_ko.yaml` | RapidOCR 설정 |
| `weights/` | 영역 찾는 모델과 글자 읽는 모델 |
